## 1. 목표와 성공 기준

AI가 매일 정해진 시각에 독거 어르신께 전화를 걸어 안부를 묻고, 통화 내용에서 **정서 위험 신호를 결정론적으로 측정**해 보호자에게 알린다.

**성공 기준은 캡스톤 + 창업경진대회입니다.**

1. 실제 전화로 끊김 없이 도는 3분 시연 (발신 → 대화 → 종료 → 리포트 → 알림)
2. 심사에서 설명할 수 있는 기술적 차별점 — **위험 점수의 재현성**

두 번째가 간판입니다. 감정 점수를 LLM이 산출하면 같은 대화에 다른 숫자가 나오고, 보호자는 몇 번 겪은 뒤 알림을 무시하게 됩니다. **알림을 신뢰할 수 있게 만드는 것**이 이 서비스의 존재 이유입니다.

### 측정 가능한 목표

| 항목 | 목표치 |
|---|---|
| 예약된 통화의 실제 발신 성공률 | 95% 이상 |
| 어르신 발화 종료 → AI 응답 시작 (체감 지연) | **3초 이내** |
| 통화 종료 → 보호자 리포트 생성 | 3분 이내 |
| **같은 오디오 재분석 시 위험 점수 편차** | **0 (완전 재현)** |
| 우울 의심 감지 재현율 (골든셋 20건) | 80% 이상 |
| 오탐 억제 (정밀도) | 70% 이상 |

## 2. 범위

### 포함

- **두 채널의 AI 대화** (3~5분) — 아래 3.0
  - **전화망(pstn)** — 스케줄 기반 자동 발신. 매일 정해진 시각
  - **앱(app)** — 어르신이 늘봄 앱에서 "AI 친구"를 눌러 아무 때나
- 통화 녹음 → STT 전사 → 대화 저장
- **결정론적 위험 지표 산출** (발화량·침묵·응답지연·부정표현·미응답 이력)
- LLM 기반 통화 요약 및 보호자용 설명 문장
- 위험 수준 상승 시 보호자 SMS/이메일 알림
- **어르신용 앱** (늘봄) — AI 통화, AI 채팅, 비상 연락, 통화 기록
- 보호자 대시보드 (통화 목록, 대화 내용, 위험 추이 그래프)

### 제외 (의도적)

| 제외 항목 | 이유 |
|---|---|
| **인바운드(어르신이 거는 080)** | 한국 080은 국내 통신사만 발급하며 Twilio에 없음(3.1). 4주 범위 밖 |
| 긴 대화(30분+) | 통화당 STT·LLM 비용이 선형 증가. MVP는 3~5분 |
| 정식 회원 시스템 | 보호자 로그인은 최소 구현. 소셜 로그인·권한 등급 제외 |
| RAG / 벡터 검색 | 위험 판정에 불필요. 대화 품질 개선은 프롬프트로 |
| 복지사 대시보드 | 보호자 하나로 충분히 시연 가능 |
| 보호자용 네이티브 앱 | 보호자는 앱 안의 보호자 화면 또는 웹 대시보드로 충분 |

### 트랙 분리

**대시보드(프론트엔드)는 별도 트랙으로 후반 합류합니다.** 통화 파이프라인을 먼저 완성하고, 그 사이 프론트는 5장 JSON 계약에 맞춘 fixture로 개발합니다.

## 3. 핵심 설계 결정

### 3.0 어르신에게 닿는 길은 둘이다 — 전화망과 앱

한 가지 길만으로는 부족합니다.

| | **전화망 (pstn)** | **앱 (app)** |
|---|---|---|
| 누가 시작 | **AI가 건다** (매일 정해진 시각) | **어르신이 누른다** (아무 때나) |
| 어르신이 할 일 | 전화를 받는다 | 앱을 열고 "AI 친구"를 누른다 |
| 오디오 | G.711 μ-law **8kHz** | **16kHz 이상** (PCM) |
| 경로 | ClawOps 070 + Asterisk (3.1) | WebSocket → 서버 (3.1-a) |
| `calls.channel` | `'pstn'` | `'app'` |

**왜 둘 다인가.**

- **앱만 두면** AI가 먼저 찾아갈 수 없습니다. 이 서비스의 존재 이유는 *어르신이 아무 말이 없을 때 그걸 알아채는 것*인데, 어르신이 눌러야만 대화가 생기면 **가장 위험한 분이 가장 적게 기록됩니다.** 미응답 이력(3.2)도 성립하지 않습니다.
- **전화망만 두면** 어르신이 외로울 때 먼저 손 내밀 방법이 없습니다. 하루 한 번 정해진 시각 말고는 접점이 없습니다.

**두 채널은 분석 파이프라인에서 하나로 합류합니다.** VAD → 지표 → 위험 점수 → 리포트는 오디오만 들어오면 채널과 무관합니다(4장). 채널이 다르다고 점수 체계가 갈라지지 않습니다.

> **단 지표 해석에서 한 곳만 구분합니다** — **미응답 이력은 전화망 통화만 셉니다.** 앱 통화는 어르신이 직접 누른 것이라 "안 받았다"가 성립하지 않습니다. DB에서 `calls_app_cannot_be_no_answer` 제약으로 오염을 막습니다.

### 3.1 아웃바운드 주력 — 한국 080은 4주 안에 못 만든다

원 기획안의 1번 가치는 "080 무료번호로 어르신이 언제든 전화"였습니다. **성립하지 않습니다.**

- Twilio의 toll-free 제공 국가에 **한국이 없습니다.** 한국은 SMS용 모바일 번호만 제공됩니다.
- 한국 **080은 KT·SKT·LGU+가 KCC 규제 하에 발급**하며 해외 사업자가 프로비저닝할 수 없습니다.
- toll-free는 대부분의 국가에서 **국내에서만 착신** 가능합니다.
- 원 기획안 비용표에도 "전화번호(미국) $1.15/월"이라 적혀 있습니다 — 어르신이 **국제전화**를 걸어야 하고 요금은 어르신 부담입니다.

**채택: AI가 거는 방향(아웃바운드)만 구현합니다.** 원 기획안의 "자동 안부 전화"가 곁가지가 아니라 주력이 됩니다.

**부수 효과 — 발신자 식별 문제가 사라집니다.** 인바운드였다면 발신번호로 어르신을 매칭해야 하고, 번호 표시 제한이나 공중전화에서 실패합니다. 우리가 거는 구조에서는 **누구에게 걸었는지 처음부터 압니다.**

**발신 수단은 ClawOps(국내 070) + Asterisk(통화 제어·실시간 미디어) 조합으로 확정합니다.**

전화를 걸려면 ①번호 ②PSTN 트렁크 ③통화 제어가 필요한데, 이 셋을 한 업체에서 다 살 필요가 없습니다. CPaaS는 ①②를 팔지만 ③을 자기네 API 안에 가둡니다. Asterisk는 ③을 통째로 주지만 ①②가 없습니다. **서로의 빈칸을 정확히 메웁니다** — ClawOps에서 070 번호와 트렁크를 사고, 통화 제어와 실시간 미디어는 우리 Asterisk가 잡습니다.

통신 3사는 발신·통화제어 API가 없고(음성 상품은 전부 AICC = B2B 구축 계약), 국내 CPaaS(NCP SENS·NHN Cloud)는 SMS·알림톡만 제공합니다. Twilio는 실시간 오디오가 확실하지만 **한국 번호가 없어 어르신에게 해외번호로 표시**됩니다. **Twilio는 폴백으로 남깁니다.**

이 구성이 주는 것은 두 가지입니다.

- **국내 070 번호** — "해외번호라 어르신이 받지 않는다"는 제약이 사라집니다
- **실시간 양방향 오디오를 업체 지원에 기대지 않음** — Asterisk가 SIP를 종단하므로 RTP가 우리 서버로 직접 들어옵니다. 덕분에 3.3의 지연 대책이 전부 구현 가능하고, **STT·TTS·LLM 선택이 전적으로 우리 것**이라 3.5의 CLOVA 단일 스택도 지켜집니다

> **2026-09-12 확인** — ClawOps 공식 API에 **SIP Endpoints · Routes · ACLs · Credentials**가 있고, 라우트는 `sip:host[:port]`(udp/tls)로 지정합니다. **`SIP 직접연결` 애드온(월 99,000원)** 이 외부 SIP 시스템의 직접 연결을 열어 줍니다(자격증명 + IP 허용목록). 표준 SIP이므로 Asterisk 연동이 가능합니다.
>
> 같은 조사에서 **ClawOps 관리형 AI 경로에는 CLOVA가 없다는 것도 확인했습니다** — STT·LLM은 OpenAI, TTS는 Cartesia/xAI 고정이고 커스텀 엔드포인트도 실시간 오디오 스트리밍도 제공하지 않습니다. **즉 3.5(CLOVA 단일 스택)를 지키려면 Asterisk가 선택이 아니라 필수입니다.**
>
> **1주차 Day 1 확인 항목** — ① 애드온이 개인 요금제에도 붙는가(예산이 갈림, 월 118,000~198,000원) ② 무료체험에 애드온이 포함되는가 ③ 코덱이 G.711 μ-law 8kHz인가 ④ **우리가 거는 아웃바운드 방향에서 발신번호를 070으로 지정할 수 있는가**(공개 문서는 ClawOps → 우리 SIP URI 방향 위주) ⑤ 사업자등록 필요 여부. 상세와 갈래별 판단 기준은 `docs/telephony-implementation.md` 4장.

### 3.1-a 앱 채널은 WebSocket으로 PCM을 주고받는다

앱 통화에는 **전화망도 SIP도 개입하지 않습니다.** 어르신 휴대폰과 우리 서버가 직접 연결됩니다.

```
[늘봄 앱]  ──── WebSocket (PCM 16kHz, 20ms 프레임) ────▶  [대화 핸들러]
    ▲                                                          │
    └──────────── AI 응답 오디오 (같은 소켓) ──────────────────┘
```

**WebRTC를 쓰지 않습니다.** WebRTC는 STUN·TURN·ICE·SDP 협상이 따라붙는데, 우리는 브라우저 간 P2P가 아니라 **앱 ↔ 우리 서버** 한 방향뿐입니다. 서버 주소가 고정이므로 NAT 순회가 필요 없고, 일반 WebSocket으로 PCM을 흘리면 끝납니다. 4주 안에 확실히 되는 쪽을 택합니다.

**전화망보다 오히려 쉽고 좋습니다.**

- **음질이 낫습니다** — 8kHz μ-law 압축을 거치지 않습니다. STT 인식률에 그대로 유리합니다
- **VAD가 이미 검증돼 있습니다** — `VadSegmenter`의 원본 테스트 8개가 **16kHz 기준**입니다. 8kHz 전화망 테스트 6개는 그 뒤에 추가한 것입니다
- **비용이 0원입니다** — 통화료도, 070 번호도, SIP 애드온도 없습니다

**대화 핸들러는 두 채널이 공유합니다.** 전화망은 Asterisk AudioSocket에서, 앱은 WebSocket에서 프레임이 들어오는 차이뿐이고, 그 뒤(발화 종료 감지 → 즉시 반응 오디오 → CLOVA 왕복)는 같은 코드입니다.

> **시연에서 강합니다.** 심사위원 앞에서 실제 전화를 거는 건 통신망 상태에 기댄 도박이지만, 앱 통화는 그 자리에서 눌러 보여줄 수 있습니다. 전화망 시연이 실패해도 앱으로 이어갈 수 있습니다.

### 3.2 위험 점수는 LLM이 만들지 않는다 ← 이 프로젝트의 간판

원 기획안은 `emotion_score INT 0~100`을 GPT가 산출하게 되어 있었습니다. 이러면 같은 대화에 오늘 62점, 내일 71점이 나옵니다. **추이 그래프가 노이즈가 되고, 알림을 신뢰할 수 없게 됩니다.**

**점수는 결정론적 지표의 가중합으로 계산하고, LLM은 그 숫자를 사람 말로 설명하는 역할만 합니다.**

| 지표 | 계산 | 출처 |
|---|---|---|
| 발화 비율 | 어르신 발화 시간 / 통화 시간 | VAD |
| 평균 응답 지연 | AI 발화 종료 → 어르신 발화 시작 | VAD + 통화 로그 |
| 침묵 비율 | 무음 구간 합 / 통화 시간 | VAD |
| 발화 턴 수 | 어르신 발화 구간 개수 | VAD |
| 부정 표현 빈도 | 사전 매칭 (아프다/힘들다/외롭다/귀찮다…) | 전사문 |
| 미응답 이력 | 최근 7회 중 미응답 횟수 | 통화 기록 |
| **추세** | 위 지표의 2주 이동 변화량 | 계산 |

**절대값보다 변화가 중요합니다.** 원래 말수가 적은 분과 갑자기 말수가 준 분은 다릅니다. 위험 판정은 **개인 기준선 대비 변화**로 합니다.

```
앱/전화: 통화 오디오
     ↓
서버: VAD로 발화/침묵 구간 확정 → 지표 계산 (결정론적)
      STT 전사 → 부정 표현 사전 매칭 (결정론적)
      → risk_score, risk_level 확정
     ↓ (전사문 + 이미 확정된 지표만 전달)
LLM: 통화 요약 + 보호자용 설명 문장 (숫자 산출에 관여하지 않음)
     ↓
보호자: 서버가 계산한 숫자를 그래프로, LLM 문장은 "설명"으로
```

> **발표 답변:** "감정 점수를 AI가 지어내지 않습니다. 음성에서 직접 잰 지표로 계산하므로 같은 통화는 항상 같은 점수가 나옵니다. AI는 그 숫자를 사람 말로 옮길 뿐입니다."

이전 프로젝트(`archive/interview-coach/`)의 **`VadSegmenter`가 발화량·침묵·응답지연을 재는 코드 그 자체**입니다. 테스트 8개로 검증돼 있고 외부 의존이 없어 그대로 이식합니다. `FillerDetector`의 사전 매칭 로직도 부정 표현 탐지로 거의 그대로 옮겨집니다.

### 3.3 전화에서 3초 침묵은 통화 종료 신호다

원 기획안은 녹음→STT→LLM→TTS 왕복을 "2~3초, 어르신은 못 느낄 수준"으로 봤습니다. 실제로는 STT 1~2초 + LLM 1~3초 + TTS 1~2초 + 네트워크로 **4~8초**입니다. 화면이 없어 "처리 중"을 보여줄 수도 없고, 어르신은 "여보세요?" 하다 끊습니다.

**아래 세 대책은 통화 중 양방향 실시간 오디오를 전제로 합니다.** Asterisk가 SIP를 종단하므로 RTP는 우리 서버로 직접 들어옵니다(3.1) — 실시간 오디오 자체는 업체 지원에 달려 있지 않습니다. 다만 ClawOps가 SIP 트렁크를 열어 주지 않아 REST 구성으로 내려가는 경우에는, 턴 기반으로 낮추고 체감 지연 목표를 6초로 완화합니다. 그래도 TTS 캐시(대책 2)는 그대로 유효하며 오히려 더 중요해집니다.

**지연을 세 겹으로 흡수합니다.**

1. **즉시 응답 오디오** — 어르신 발화 종료를 감지하는 즉시, 사전 생성해 둔 짧은 반응("네~", "그러셨구나")을 **0.5초 내에** 재생합니다. 그 뒤에서 STT·LLM·TTS가 돕니다.
2. **TTS 사전 생성 캐시** — 규칙 기반으로 처리되는 응답(원 기획안 기준 90%)은 **미리 음성 파일로 만들어 S3에 두고** 그대로 재생합니다. 이 경로의 지연은 사실상 0입니다.
3. **응답 길이 상한** — LLM 응답은 2문장 이내로 강제합니다. 길수록 TTS 생성이 느려집니다.

즉 **"규칙 기반 90%"는 비용 절감책이 아니라 지연 대책**입니다. 이 관점이 원 기획안에 없었습니다.

### 3.4 API 계층은 분석하지 않는다

통화 중에는 **응답이 몇 초만 늦어도 통화가 끊깁니다.** 그래서 통화 중에는 짧은 응답만 다루고, STT 전체 전사와 LLM 요약·지표 계산은 **통화가 끝난 뒤** 비동기로 처리합니다.

- 통화 중: **Asterisk AudioSocket**으로 오디오를 주고받음. 턴마다 웹훅을 왕복하지 않음
- 통화 후: 녹음 파일 → SQS → 워커(전사 · 지표 계산 · LLM 요약 · 알림 판정) → DB
- 보호자 대시보드: 저장된 결과를 조회

### 3.5 음성·언어를 CLOVA 한 스택으로

STT · TTS · LLM을 모두 네이버로 통일합니다.

| 용도 | 서비스 |
|---|---|
| 음성 → 텍스트 | CLOVA Speech Recognition (한국어 특화, 노인 음성·사투리에 상대적으로 강함) |
| 텍스트 → 음성 | CLOVA Voice (TTS) |
| 대화 응답 · 요약 | **CLOVA Studio (HyperCLOVA X)** — `HCX-DASH-002` 계열(경량·저가)을 기본, 필요 시 `HCX-005`/`HCX-007` |

계정·인증·과금이 하나로 묶이고, 한국어 노인 대화라는 도메인에 맞습니다. 입력·출력 토큰이 분리 과금되므로 **응답 길이 상한(3.3)이 비용 통제와 직결**됩니다.

> 엔진별 단가와 쿼터는 NAVER Cloud Platform 콘솔에서 1주차에 실측합니다. 사용 전 이용 신청이 필요합니다.

### 3.6 동의와 개인정보를 설계에 넣는다

노인 음성 녹음 + 정서 상태 추정은 민감한 데이터입니다. 원 기획안에는 동의 절차가 없었습니다. 창업경진대회에서 반드시 나오는 질문입니다.

- **보호자 등록 시** 어르신 동의 확인을 필수 입력으로 두고 `elders.consent_at`에 기록합니다
- **첫 통화 도입부**에 음성 고지: "안부 확인을 위해 통화 내용이 기록됩니다"
- **원본 오디오는 분석 완료 후 30일 내 삭제**, 전사 텍스트와 지표만 보관합니다
- 위험 판정은 **의료 진단이 아니라 조기 경보**임을 대시보드에 명시합니다

### 컴포넌트 책임과 의존

| 컴포넌트 | 책임 | 의존 | 독립 테스트 |
|---|---|---|---|
| `MediaHandler` | 통화 중 대화 진행 (AudioSocket 송수신) | Asterisk, CLOVA | 녹음 파일 재생으로 대체 검증 |
| `VadSegmenter` | 오디오 → 발화/침묵 구간 | 없음 (순수) | 합성 오디오, 로컬 |
| `MetricsCalculator` | 구간 + 전사문 + 이력 → 점수·위험도 | **없음 (순수)** | fixture만으로 |

| `ReportWriter` | 지표 + 전사문 → 요약 문장 | CLOVA Studio | 지표 모킹 주입 |

**`MetricsCalculator`가 순수 함수인 것이 3.2의 구조적 표현입니다.** 점수 산출에 네트워크도 LLM도 개입하지 않으므로, 같은 입력이면 반드시 같은 점수가 나옵니다.

### 5.1 통화 결과 조회 — `GET /v1/calls/{call_id}`

```json
{
  "call_id": 1042,
  "elder_id": 7,
  "status": "completed",
  "call_type": "outbound",
  "started_at": "2026-09-07T09:00:12+09:00",
  "duration_seconds": 214,
  "analysis": {
    "transcript": [
      { "speaker": "ai",    "text": "어르신 안녕하세요, 오늘 아침은 드셨어요?", "start_ms": 0 },
      { "speaker": "elder", "text": "응... 그냥 뭐 대충 먹었지", "start_ms": 4200 }
    ],
    "metrics": {
      "speech_ratio": 0.31,
      "silence_ratio": 0.52,
      "avg_response_delay_ms": 2840,
```

## 6. 데이터 모델

전체 DDL은 `db/schema.sql`, ERD는 `db/erd.md`에 있습니다.

`guardians` → `elders` → `calls` → `call_metrics` / `call_transcripts` / `call_reports`, 그리고 `alerts`.

### 원 기획안 대비 변경

| 변경 | 이유 |
|---|---|
| **테이블 정의 순서 수정** | 원 DDL은 `elders`가 `REFERENCES guardians(id)`를 선언하는데 `guardians`가 **그 아래** 정의됨. PostgreSQL은 전방 참조를 허용하지 않아 `relation "guardians" does not exist`로 **실행 자체가 실패**함 |
| **`emotion_analyses`를 둘로 분리** — `call_metrics`(결정론적 지표·점수) + `call_reports`(LLM 요약) | 3.2의 구조적 표현. 한 테이블에 두면 "이 숫자를 누가 만들었나"가 흐려짐 |
| **`calls.status` 신설** | 원 스키마는 미응답·발신실패를 표현할 수 없었음(`ended_at` NULL로만 추정) |
| **`elders.consent_at` 신설** | 동의 기록이 없었음(3.6) |
| **`elders.baseline_*` 신설** | 개인 기준선 저장. 절대값이 아닌 변화로 판정하기 위함 |
| CHECK 제약 추가 | `call_type`, `status`, `alert_type`, `severity`, `risk_level` 등 |

## 7. AI 파이프라인 상세

### 7.1 서비스와 모델

| 용도 | 서비스 / 모델 | 비고 |
|---|---|---|
| STT | CLOVA Speech Recognition | 한국어 특화. 노인 음성·사투리 인식률을 1주차 실측 |
| TTS | CLOVA Voice | 규칙 응답은 **사전 생성해 S3 캐시**(3.3) |
| 대화·요약 | CLOVA Studio (HyperCLOVA X) — `HCX-DASH-002` 기본 | 입력·출력 토큰 분리 과금 |

> 엔진 단가·쿼터·이용 신청은 NCP 콘솔에서 1주차에 확인합니다. 사용 전 신청이 필요합니다.

### 7.2 호출 규약

CLOVA Studio는 REST 기반이며 NCP 인증 헤더를 사용합니다. 반드시 지킬 것:

- **응답 길이를 프롬프트와 파라미터 양쪽에서 제한** — 2문장 이내. 지연과 비용에 직결됩니다.
- **출력은 JSON 스키마를 프롬프트로 강제하고 `json.loads()`로 파싱**합니다. 문자열 매칭 금지.
- **요약 프롬프트에 지표를 주입하되 "숫자를 새로 만들지 말 것"을 명시**합니다. 반환된 문장에 숫자가 있으면 서버가 계산한 값과 대조해 불일치 시 문장을 폐기합니다.
- 시스템 프롬프트(페르소나·톤·출력 규격)는 고정, 통화별 가변 데이터는 뒤에 배치합니다.
- 타임아웃·재시도는 구체적인 것부터 체인으로 처리해 재시도 가능/불가능한 실패를 구분합니다.

### 7.3 대화 전략 — 규칙 90% / LLM 10%

```
어르신 발화
   ↓
[의도 분류]  사전·패턴 기반
   ├─ 인사/식사/날씨/건강 등 정형 →  캐시된 TTS 오디오 즉시 재생 (지연 ~0)
   └─ 그 외 →  즉시 반응 오디오 재생 + CLOVA Studio 호출 → TTS → 재생
```

정형 응답 세트는 1주차에 30~50개를 미리 만들어 S3에 올려둡니다.

### 7.4 비용 조절 순서

1. **캐시 히트율 확인** — 규칙 응답 비율이 높을수록 비용·지연이 함께 내려갑니다
2. 응답 길이 상한(2문장) 준수 여부 확인
3. 통화 길이 상한(5분) — STT는 시간당 과금이라 여기가 가장 큽니다
4. 그래도 부족하면 엔진 하향(`HCX-DASH-002`) 및 요약 주기 조정

## 8. 에러 처리

| 상황 | 처리 |
|---|---|
| 미응답 / 통화 거부 | `status='no_answer'` 기록 + 보호자 알림. **실패가 아니라 지표**입니다 — 미응답 이력이 위험 점수에 반영됩니다 |
| 발신 자체 실패 | `status='failed'` + `CALL_FAILED`. 스케줄러가 30분 뒤 1회 재시도 |
| 통화 중 웹훅 지연/오류 | 사전 캐시 오디오로 폴백("잘 안 들리네요, 다시 말씀해 주시겠어요?") |
| STT 실패·저품질 | 지표 중 전사문 기반 항목(부정 표현)만 제외하고 VAD 기반 항목은 유지, `degraded: true` |
| VAD 실패(잡음 과다) | 발화 지표 산출 생략, `risk_score: null` + `degraded: true`. 임의 점수를 만들지 않습니다 |
| LLM 요약 실패 | 지표와 그래프는 정상 노출, 요약만 "요약 생성 실패" 표시. **부분 성공 허용** |
| LLM 응답에 서버 계산과 다른 숫자 | 해당 문장 폐기 + 경고 로그 (7.2) |
| 폴링 중 잡 소실 | 404 대신 `status: "failed"` + `INTERNAL` 반환 |

| `VadSegmenter` | 합성 오디오 → 기대 구간 (이전 프로젝트 테스트 8개 이식) |
| `MetricsCalculator` | **순수 함수 단위 테스트.** fixture(구간 + 전사문 + 과거 통화) → 기대 점수·위험도. 오디오·네트워크 불필요 |
| `Transcriber` | 샘플 통화 오디오 20건 인식률 실측 |
| `ReportWriter` | 지표 모킹 주입. 출력 스키마 + **숫자 불일치 폐기 로직** 단위 테스트 |
| API 계층 | fixture로 웹훅 → 큐 → 결과 왕복 검증 |
| E2E | 실제 전화 발신 → 리포트 생성 (팀원 번호로) |

### 9.2 골든 평가셋

**정답 라벨을 붙인 통화 오디오 20건.** 각 건에 "이 통화는 정상/주의/경보"를 사람이 미리 판정하고, 발화 구간과 부정 표현 위치를 태깅합니다.

이것이 있어야 임계값을 근거 있게 정할 수 있고, 발표에서 "재현율 82%" 같은 숫자를 쓸 수 있습니다. 측정 항목: 위험 감지 재현율/정밀도, 지표별 기여도, 발화 구간 경계 오차.

> **재현성 테스트를 별도로 둡니다.** 같은 오디오를 100회 분석해 `risk_score` 편차가 0인지 확인합니다. 이게 3.2의 주장을 증명하는 테스트입니다.

### 9.3 fixture

프론트 부재 기간의 입력원입니다. 5.1~5.3 형식 JSON을 정상·주의·경보 3종으로 만듭니다. 프론트 합류 후 실측값으로 교체하며 회귀 테스트 자산으로 남습니다.

| 트랙 | 인원 | 범위 |
|---|---|---|
| **A. 전화 파이프라인** | 1명 전담 | Asterisk 구축(ClawOps 트렁크·ARI·AudioSocket), CLOVA STT/TTS 연동, TTS 캐시, 지연 대책 |

| **D. 계약 & 평가셋** | 겸임 (B/C 분담) | fixture, 골든 평가셋 20건, 정확도 측정 스크립트 |

**3주차 재배치** — 대시보드 전담이 없으므로, 분석 코어가 안정화되는 3주차에 B 담당자 1명이 프론트로 이동합니다. 2주차 말까지 안정화되지 못하면 임계값 튜닝을 중단하고 1주차 기본값으로 확정한 뒤 이동합니다. **지표 정밀도보다 데모 완성도가 우선입니다.**

```
[1주차] 계약 고정 + 실측
 ├─ (전원) 5장 JSON 계약 확정 — 최우선
 ├─ A: **ClawOps SIP 트렁크 확인(최우선)** → Asterisk 발신 Hello World + AudioSocket 오디오 수신 실측, CLOVA STT/TTS 인식률·지연, NCP 이용 신청
 ├─ B: VadSegmenter 이식 + MetricsCalculator TDD 착수, 부정 표현 사전 초안
 └─ C: RDS·S3·SQS·EventBridge 프로비저닝, API 스켈레톤 배포

[2주차] 파이프라인 완성
 ├─ A: 통화 흐름 완성(발신 → 대화 → 종료 콜백), TTS 캐시 30~50개 생성
 ├─ B: MetricsCalculator 완성, 기준선·추세 로직, ReportWriter 연결
 ├─ C: SQS 워커 배선, 조회 API 완성 → fixture로 E2E 왕복
 └─ D: 골든 평가셋 20건 라벨링

[3주차] 대시보드 합류
 ├─ 보호자 대시보드(통화 목록·대화 내용·추이 그래프·알림)
 ├─ B/D: 평가셋 기반 임계값 튜닝, 재현성 테스트
 └─ C: SMS/이메일 알림, 발신 스케줄러 실운영

[4주차] 완성도와 시연
 ├─ 동의 고지 음성, 데이터 보관·삭제 정책 구현
 ├─ 프리셋 시나리오(정상/주의/경보 3종) 정비
 ├─ 실제 전화 E2E 테스트, 예외 경로 정리
 └─ 발표 시연 플로우 확정 + 리허설
```
