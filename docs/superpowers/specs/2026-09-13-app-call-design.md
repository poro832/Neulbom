# 앱 채널 통화 — 설계 문서

- **팀명:** 공명
- **작성일:** 2026-09-13
- **범위:** 설계 문서 3.1-a(앱 채널)의 구현 설계
- **상태:** 설계 확정, 구현 착수 전

> 상위 설계는 `docs/superpowers/specs/2026-09-07-ansimcare-design.md` 3.0(두 채널) / 3.1-a(앱 채널)입니다. 이 문서는 그 3.1-a를 실제로 어떻게 만들지만 다룹니다.

---

## 1. 목표

어르신이 늘봄 앱에서 **"AI 친구"를 누르면 말이 오가게** 만든다.

```
어르신 앱 ──WebSocket PCM 16kHz──▶ 서버
    ▲                                │
    │                        발화 종료 감지
    │                                ▼
    └───────── 응답 오디오 ──────────┘
```

### 이번 범위 — "골격까지"

CLOVA는 NCP 이용 신청이 끝나지 않아 지금 호출할 수 없습니다. **인터페이스만 맞춰 두고 고정 응답으로 대체**합니다. 규약을 먼저 세워 두면 나중에 `CallSession` 안쪽을 건드리지 않고 갈아끼울 수 있습니다.

> 단, **골격의 동기 규약 그대로는 못 갈아끼웁니다.** 3장과 2장의 ⚠️ 두 개가 `ClovaResponder`의 선결 조건입니다.

| 포함 | 제외 |
|---|---|
| 스트리밍 VAD — 발화 종료 감지 | CLOVA 실호출 (`CannedResponder`로 대체) |
| WebSocket 양방향 PCM | DB · S3 · 인증 |
| 즉시 반응 오디오 송출 | 배치 VAD·지표 연결 (wav 저장까지만) |
| 통화 원본 누적 → wav 저장 | barge-in (타입만 예약) |

---

## 2. 핵심 결정 — VAD를 둘로 나눈다

이 설계에서 가장 중요한 판단입니다.

| | **스트리밍 VAD** (신규) | **배치 VAD** (기존) |
|---|---|---|
| 묻는 것 | "어르신이 말을 멈췄나?" | "발화 구간이 정확히 어디였나?" |
| 쓰이는 곳 | 응답 타이밍 | 위험 지표 |
| 입력 | 프레임이 도착하는 대로 | 통화 전체 녹음 |
| 요구사항 | 빠를 것. **근사해도 무방** | **완전 재현** |

**스트리밍 결과를 지표에 쓰면 설계 3.2의 재현성이 깨집니다.** 프레임 도착 타이밍·네트워크 지연에 따라 판정이 달라지기 때문입니다. 같은 통화를 다시 분석해도 같은 점수가 나와야 한다는 것이 이 프로젝트의 간판인데, 그게 무너집니다.

그래서 **통화 중에는 스트리밍 VAD가 턴만 잡고, 통화가 끝나면 녹음 전체에 기존 `segment_audio`를 그대로 돌려** 지표를 냅니다. 기존 테스트 34개는 손대지 않습니다.

> ⚠️ **이 논증은 오디오 경로만 덮습니다 — 2026-09-13 최종 리뷰에서 드러난 구멍입니다.**
>
> `CallSession`은 **스트리밍 경계로 자른** 오디오를 `Responder`에 넘깁니다. 지금은 `CannedResponder`가 전사문을 만들지 않아 문제가 없지만, `ClovaResponder`가 붙으면 그 오디오가 전사문이 되고 `MetricsCalculator`는 **전사문을 지표 입력으로 씁니다**(부정 표현 빈도). 즉 재현성이 오디오가 아니라 **텍스트 경로로 샙니다.**
>
> **`ClovaResponder`의 선결 조건:** 지표에 쓰는 전사문은 통화 중 스트리밍 결과가 아니라 **통화 후 wav를 배치 VAD 구간으로 다시 전사한 것**이어야 합니다. 통화 중 전사는 대화 진행용으로만 쓰고 지표에 넣지 않습니다.

### 스트리밍 임계값 — 롤링 윈도우

기존 `_adaptive_threshold`는 **전체 신호의 백분위**를 씁니다.

```python
quiet = float(np.percentile(frame_rms, 10))
peak  = float(np.percentile(frame_rms, 95))
noise = min(quiet, peak * _NOISE_PEAK_CAP)
return max(DEFAULT_NOISE_FLOOR, noise * DEFAULT_NOISE_FACTOR)
```

아직 도착하지 않은 오디오의 백분위는 구할 수 없습니다. **최근 3초(150프레임)만 들고 같은 공식을 매 프레임 다시 계산**합니다.

검토한 대안과 탈락 사유:

| 방법 | 탈락 사유 |
|---|---|
| 초반 1초로 보정 후 고정 | 어르신이 바로 말을 시작하면 보정이 오염됨. 중간에 TV가 켜지면 대응 불가 |
| EMA 잡음 바닥 | O(1)로 싸지만 **배치와 다른 알고리즘**이 됨. 두 벌이 갈라짐 |

롤링 윈도우의 알려진 함정은 *"윈도우가 발화로 가득 차면 잡음 추정이 올라가 자기 발화를 지운다"* 인데, **`_NOISE_PEAK_CAP = 0.3`이 이미 그걸 막고 있습니다.** 8kHz 버그를 고칠 때 넣은 가드가 여기서 다시 값을 합니다.

**공식이 하나로 유지된다**는 것이 이 선택의 이유입니다.

### 턴 종료 판정

발화 종료는 음절 사이 공백(`DEFAULT_MIN_SILENCE_MS = 300`)과 다릅니다. 어르신은 천천히, 중간에 쉬면서 말씀하십니다.

```
침묵 800ms 지속  →  발화 종료로 판정
       ↓ 0.5초 내
즉시 반응 오디오 재생
```

체감 ≈ 1.3초. 설계 3.3의 "3초 이내"에 들어갑니다. 실제 통화 후 조정할 자리입니다.

## 3. 컴포넌트

```
app/media/
├─ streaming_vad.py   StreamingVad     ← 순수. 프레임 → 발화 종료
├─ responder.py       Responder 규약 + CannedResponder
├─ session.py         CallSession      ← 한 통화의 상태. 전송 수단 모름
└─ ws_server.py       WebSocket 어댑터  ← 얇게. 바이트만 옮김
```

| 컴포넌트 | 책임 | 의존 | 독립 테스트 |
|---|---|---|---|
| `StreamingVad` | `push(frame)` → `None` \| `SpeechEnded` | **없음 (순수)** | 합성 오디오 |
| `Responder` | 발화 → 응답 오디오 | 골격에선 없음 | — |
| `CallSession` | VAD 구동 · 응답 요청 · 원본 누적 | 위 둘 | 가짜 Responder |
| `ws_server` | 소켓 ↔ 세션 배관 | FastAPI | 통합 1~2개 |

**`CallSession`이 WebSocket을 모릅니다.** 소켓 없이 바이트를 밀어넣고 나오는 것을 보면 되므로 테스트가 쉽습니다. 나중에 전화망(Asterisk AudioSocket)이 붙을 때도 `CallSession`은 그대로 재사용됩니다 — 프레임 출처만 다릅니다.

**`Responder`를 규약으로 분리**해 둡니다.

> ⚠️ **"교체가 한 줄"은 틀렸습니다 — 같은 리뷰에서 드러났습니다.**
>
> `respond()`가 **동기**인데 async 소켓 루프 안에서 호출됩니다. `CannedResponder`는 즉시 반환해 테스트가 이 문제를 가립니다. `ClovaResponder`는 Speech → Studio → Voice로 HTTP 3회 왕복(약 1~3초)이라, 그동안 **이벤트 루프가 막혀 동시 통화 전체의 프레임 타이밍이 무너집니다.**
>
> **`ClovaResponder`의 선결 조건:** 규약을 `async def respond(...)`로 바꾸거나, `CallSession`이 "응답이 필요하다"는 메시지를 돌려주고 **어댑터가 await를 맡는** 구조로 바꿔야 합니다. 후자가 `CallSession`을 I/O 없는 순수 계층으로 유지해 더 낫습니다. 골격에서 미룬 이유는 모양을 검증할 async 소비자가 아직 없기 때문입니다.

## 4. 프로토콜

한 소켓에서 **바이너리는 소리, 텍스트는 신호**로 나눕니다.

```
앱 → 서버
  binary : PCM16 mono 16kHz little-endian (20ms = 640 bytes)
  text   : {"type":"start","sample_rate":16000}
           {"type":"end"}

서버 → 앱
  binary : 응답 오디오 (같은 포맷)
  text   : {"type":"speech_end"}      화면 표시용
           {"type":"stop_playback"}   ← 자리만. 골격에선 안 보냄
```

`stop_playback`을 지금 정의하는 이유는, 나중에 barge-in을 켤 때 **앱을 다시 배포하지 않아도 되게** 하려는 것입니다.

### 통화 흐름

```
앱: {"type":"start"}
앱: ─── PCM 프레임들 ───▶  StreamingVad.push()
                              │
                        침묵 800ms 누적
                              ▼
                          SpeechEnded
                              │
                     Responder.respond()
                              ▼
서버: {"type":"speech_end"} + 응답 오디오 바이너리
앱: {"type":"end"}
                              ▼
                    누적 원본을 .wav로 저장
```

## 5. 에러 처리

| 상황 | 처리 |
|---|---|
| 프레임이 640바이트로 안 옴 | 버퍼에 모아 경계를 맞춰 처리 |
| `start` 없이 오디오 도착 | 무시 |
| 샘플레이트 불일치 | **연결 거부** — 조용히 틀린 결과보다 낫다 |
| 앱이 갑자기 끊김 | **누적분을 wav로 저장**하고 정리. 통화 기록이 사라지면 안 된다 |
| 저장 경로 | `recordings/{call_id}.wav` (로컬). `call_id`는 서버가 발급한 UUID. S3는 다음 단계 |
| `Responder` 예외 | 로그만 남기고 응답 생략. **통화는 유지** |

마지막 둘이 상위 설계 8장(부분 성공 허용)과 같은 원칙입니다. 응답 하나 실패했다고 통화를 끊으면 어르신은 영문을 모릅니다.

## 6. 테스트

`StreamingVad`가 무게중심입니다. 순수 함수라 합성 오디오만으로 전부 검증됩니다.

| 테스트 | 무엇을 고정하나 |
|---|---|
| 조용한 목소리도 잡는다 | 8kHz에서 찾은 그 버그의 16kHz 형제 |
| 음절 사이 300ms 공백은 종료가 아니다 | 말 중간에 끊고 들어가지 않음 |
| 침묵 800ms에서 종료 판정 | 턴 전환 타이밍 |
| 잡음만 흐르면 이벤트 없음 | 헛응답 방지 |
| 처음부터 끝까지 발화여도 자기 발화를 안 지운다 | `_NOISE_PEAK_CAP`이 스트리밍에서도 도는지 |
| **프레임이 쪼개져 와도 결과가 같다** | 네트워크가 640바이트로 안 잘라 줌 |

마지막이 중요합니다. WebSocket은 보낸 단위로 도착한다는 보장이 없어서, **버퍼링이 깨지면 조용히 어긋납니다.**

`CallSession` — 가짜 `Responder`로: 발화 종료 시 호출되는가, 원본이 누적되는가, **응답 생성이 실패해도 통화가 안 죽는가**.

`ws_server` — 얇으므로 통합 테스트 1~2개.

## 7. 기존 코드에 손대는 곳

**`_adaptive_threshold`를 공개로 올립니다.**

지금은 비공개인데 `StreamingVad`가 써야 합니다. 복사하면 **두 벌이 갈라지므로** — 공식이 하나라는 게 2장의 전제입니다 — `adaptive_threshold`로 이름만 바꿔 공유합니다.

**`pyproject.toml`에 서버 의존성을 추가합니다.**

```toml
dependencies = ["numpy>=2.0", "fastapi>=0.115", "uvicorn[standard]>=0.30"]
dev = ["pytest>=8.0", "httpx>=0.27"]   # httpx는 WebSocket 통합 테스트용
```

이 둘 외에는 기존 코드를 건드리지 않습니다. **기존 테스트 34개가 그대로 통과해야 합니다.**

## 8. 다음 단계

이 골격이 서면 이어지는 것들입니다. **이번 범위 밖입니다.**

- `CallSession`이 저장한 wav → 배치 VAD → `MetricsCalculator` → DB (`calls.channel = 'app'`)
- `ClovaResponder` — CLOVA Speech → Studio → Voice
- barge-in — `stop_playback` 송신 + 앱 재생 버퍼 비우기
- **마이크 스트림에 섞인 AI 음성** — 스피커폰이면 녹음에 AI 응답이 되울려 들어가고, 배치 VAD가 그걸 어르신 발화로 셉니다. 결정론적이라 재현성은 유지되지만 **지표가 틀립니다.** 설계·계획 어디에도 없던 항목입니다
- **스트림 종료 시 열린 턴** — `respond()`가 호출되지 않아 그 턴의 전사문이 생기지 않습니다. 음향 지표는 wav에서 나오므로 무사하지만 전사문 기반 지표는 그 턴을 놓칩니다
- 전화망 채널 — 같은 `CallSession`에 Asterisk AudioSocket을 물림
